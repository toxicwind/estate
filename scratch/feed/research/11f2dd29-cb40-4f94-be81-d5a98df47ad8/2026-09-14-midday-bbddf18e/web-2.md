## Finding 1
vLLM shipped v0.29.0 (594 commits from 277 contributors). The GitHub release page itself states no publication date in its rendered text and was indexed around September 11, 2026; it is the newest release on the project's releases page. Headline change: Model Runner V2 is now the default runner for all models, and the notes declare MRV1 deprecated with removal targeted at v0.32; vLLM still falls back to MRV1 for features MRV2 does not yet support (sequence parallelism, dual-batch overlap, elastic expert parallelism, custom logits processors, certain speculative decoding methods). New defaults: FlashInfer all-reduce enabled by default for tensor-parallel CUDA groups (opt out with VLLM_ALLREDUCE_USE_FLASHINFER=0) and new --max-num-queued-reqs / --max-num-queued-tokens admission-control flags. Breaking changes: python -m vllm.entrypoints.openai.api_server is deprecated in favor of vllm serve; ten deprecated architectures removed (Arctic, Chameleon, Cheers, Fairseq2Llama, FireRedLID, GritLM, HCXVision, MPT, the RWForCausalLM and StableLMEpochForCausalLM aliases, and PrithviGeoSpatialMAE); FlexOlmo, Olmo3, and Hunyuan V1/VL moved to the Transformers modeling backend. Security hygiene: api_key and hf_token are now redacted from startup logs, compile cache factors, and the Rust frontend launch log. DeepSeek V4 work: shared experts fused into MegaMoE, adaptive top-k width re-landed, a native SwiGLU clamp kernel for Humming MoE, and an opt-in FlashInfer moe_ep expert backend; Kimi K3 NVFP4 checkpoints supported with fused MXFP4 top-k finalization (~5% end-to-end latency) and tuned Hopper low-latency GEMM. Mamba prefix caching via internal prefill checkpoints claims 9-25% TTFT improvement; prefix-cache NONE_HASH is now deterministic so distributed KV cache users no longer pin PYTHONHASHSEED. Default artifact is CUDA 13.0 (pip install vllm), with CUDA 12.9 wheels in GitHub assets and docker images vllm/vllm-openai:v0.29.0 (v0.29.0-cu130 also works).
- https://github.com/vllm-project/vllm/releases/tag/v0.29.0 (undated)

## Finding 2
Amazon SageMaker launched model caching for SageMaker Inference on HyperPod, now generally available in all regions where HyperPod is available. The AWS ML blog page states no publication date in its rendered text and was search-indexed as updated around September 10, 2026. Two independent capabilities: a weights cache that pre-downloads model weights to local NVMe on each node (sources: S3, FSx for Lustre, HuggingFace Hub, SageMaker JumpStart gated and non-gated) and an image cache that pre-pulls the inference server container image onto nodes via a DaemonSet. The cold-start math it is built for: vLLM or LMI container images take 5-7 minutes to pull from ECR, a 145 GB model takes 20+ minutes to download from S3, and DeepSeek-R1 at 600+ GB takes 30+ minutes; with caching, pods read from local NVMe at roughly 7 GB/s and typically serve in seconds rather than tens of minutes. Benchmarks: about 60% faster scale-out on models of 57-145 GB with weights caching enabled, and up to a 97% reduction in cold image-pull time with the image cache. Scheduling is preferred, not required: pods landing on uncached nodes fall back to normal network pulls. Limits: instance NVMe must fit the model (e.g., ml.g5.xlarge carries 250 GB, ml.p4d.24xlarge 8,000 GB, ml.p5.48xlarge 30,000 GB), source updates are not auto-detected (changing weights at the same S3 path without changing the spec keeps serving the cached version), and weights are cached per node. Enable it with a modelCacheConfig block on InferenceEndpointConfig or JumpStartModel; two new CRDs (ModelDataCacheConfig, ModelImageCache) manage the lifecycle and are inspectable with kubectl, and deleting the parent resource cleans up the cache automatically.
- https://aws.amazon.com/blogs/machine-learning/reduce-inference-cold-starts-on-amazon-sagemaker-hyperpod-with-model-caching/ (undated)

## Finding 3
A DZone piece ran controlled Ollama recovery experiments on Kubernetes measuring the gap between a pod reporting Ready and actually completing inference (Ollama, llama3.2:1b and 3b, 2 CPU / 4 GiB containers; Minikube locally on a Mac and on an Azure Standard_D16s_v5 VM; 10 repetitions per condition). The page states no publication date and was search-indexed around September 9, 2026. Kubernetes reported Ready in about 2 seconds or less in all four configurations, while functional recovery took 5.43 to 16.27 seconds; the Ready-to-inference gap ranged from about 3.8 to 14.3 seconds. Three failure modes a shallow HTTP health check misses: with emptyDir storage the runtime recovered but ollama list showed no models; a llama3.1:8b test showed the model artifact on disk with nothing resident (cgroup memory ~14 MiB, rising to ~5.27 GiB only after the first request); and loading the 3B model under a 4 GiB limit once died with signal: killed that turned out to be a still-resident 1B model overlapping, not the 3B model itself. A warm node flatters repeated tests: dropping Linux page caches raised model load 16.6% (functional recovery 7.58s warm vs 8.09s cold). The prescribed fix is an inference-aware readiness probe that exercises the model-serving path, e.g., an exec probe POSTing a minimal request (curl -sf -X POST http://localhost:11434/api/generate with model llama3.2:1b and prompt 'ping', grepping for '"done":true', periodSeconds 2, failureThreshold 1). Sampling EndpointSlice state every ~0.5s across 20 rollouts (10 local, 10 Azure), mean new-endpoint non-serving duration was 47.6s locally and 11.0s on Azure, with no sampled interval lacking a ready-and-serving endpoint. The author cautions the numbers are CPU-only, same-node replacements, not production SLAs, and cold-node relocation is measured separately.
- https://dzone.com/articles/kubernetes-llm-readiness (undated)

## Finding 4
o-mega's updated TurboQuant deployment guide (every claim re-verified September 9, 2026) gives the current KV-cache compression map. Where it actually runs: vLLM is the production path (merged April 15, PR #38479; presets live in v0.28.0, released August 26, 2026, behind --kv-cache-dtype); Qdrant shipped it in 1.18 (May 13, 2026) for vector search at 8x-32x operating points, promoted to a storage datatype in 1.19; llama.cpp's PR closed unmerged June 2 and its tracking issue closed 'not planned' August 20, so native Ollama/llama.cpp support is dead upstream; Apple MLX is the live local side door; SGLang's attempts are unshipped; Google has still released no official implementation 169 days after its March 24, 2026 announcement. The four vLLM presets form a compression-vs-quality ladder measured on Llama-3.3-70B: turboquant_k8v4 (FP8 keys + 4-bit values, 2.6x KV compression, +1.17% perplexity, GSM8K on Qwen3-4B 0.860 vs 0.900 baseline, 79-100% of baseline throughput); turboquant_4bit_nc (4-bit MSE keys + 4-bit values, 3.8x, +2.71%, GSM8K 0.840, lower throughput); turboquant_k3v4_nc (3-bit MSE keys + 4-bit values, ~3.5x, +10.63%, GSM8K 0.780, lower throughput); turboquant_3bit_nc (3-bit keys + 3-bit values, 4.9x, +20.59%, GSM8K 0.720, lowest throughput), with the guide warning the aggressive preset carries a reasoning regression risk. Scale context: a 70B-class model at 1 million-token context needs roughly 328 GB of uncompressed KV cache against about 140 GB for the weights. Enterprise data point: AWS's reference architecture built on TurboQuant lifts Llama 3.1 405B context capacity from roughly 82K to 400K+ tokens on P5en instances.
- https://o-mega.ai/articles/google-turboquant-the-2026-llm-compression-guide (published 2026-09-09)
