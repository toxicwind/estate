## 1. Verdict

**The estate uses a hybrid model: monolith as the single live runtime target, with a planned but only partially-adopted per-project D2 fragment convention.**

The live `pitchfork.toml` (35,723 bytes, 188 daemon blocks, ~69 daemons) is a **hand-edited monolith**. Pitchfork reads ONLY this file from CWD (`/home/toxic/estate`); `pitchfork config list` returns `[]` — no fragments are registered via the `config add` mechanism. The `pitchfork.d/` directory exists and contains fragment files that are **never auto-composed** by pitchfork itself.

Two separate tooling systems exist for composing fragments into the monolith, but the current `pitchfork.toml` has **never been produced by either**: it lacks the `[generated file]` stamp, schema URL, and `# ---- project:` separators that both tools emit. The monolith was hand-edited and has been hand-edited extensively (coyote env, custom readiness, health_http, port fields, comments).

**Answer to the architect's question:** Yes, there IS a per-directory convention (the D2 system), but it is NOT how the monolith was built and the fragments are NOT auto-composed by pitchfork. The `pitchfork.d/` fragments are largely dead litter — they were never registered or composed into the live config.

## 2. Composition Mechanism (or lack thereof)

### pitchfork binary's native behavior
```
$ pitchfork config list
[]                              ← empty — nothing registered

$ pitchfork config add --help
Register a configuration file for a project without copying it into the project.
Usage: pitchfork config add [--dir <DIR>] [--namespace <NAMESPACE>] <FILE>
```
Pitchfork's `config add` is for attaching external configs at runtime but **nobody has used it**. The `daemons` subcommand says "List configured daemons from all merged config files" but with zero registered configs, "all merged" = the single `pitchfork.toml`.

### Tooling system: `pf` (Design B)
**File:** `estate/bin/pf`
- `pf migrate` — splits pitchfork.toml → pitchfork.d/<name>.toml (one-time)
- `pf build` — composes pitchfork.d/ → pitchfork.toml (in-place, guarded, atomic)
- `pf diff` — lists daemons changed vs git HEAD
- `pf check` — validates fragments + composed config
- `pf explain <daemon>` — shows fragment ownership and sync state

**Source of truth declared:** `pitchfork.d/<name>.toml` (one file per daemon). The monolith stays the parent entrypoint — `pf build` rewrites ONLY its `[daemons.*]` sections.

**Guard:** `pf build` refuses to run if it detects hand-edited daemon stanzas in pitchfork.toml (three-way diff against `.hashes`).

### Tooling system: `pitchfork-compose`
**File:** `estate/bin/pitchfork-compose`
- Reads `projects.toml` for a project registry mapping keys → manifest paths
- Concatenates daemon stanzas from all project fragment directories
- Writes output with `# GENERATED by estate/bin/pitchfork-compose` header
- Atomic write via `mv`

**Design:** Inspired by systemd drop-in dirs + supervisord two-phase (parse+validate all, restart only changed).

### Tooling system: `pitchfork-split`
**File:** `estate/bin/pitchfork-split`
- One-shot migration: splits a raw monolith into D2 per-project layout
- Creates `parent.toml`, `projects.toml`, `attribution.json`, individual `<project>/pitchfork.d/<daemon>.toml`
- Refuses to split an already-composed file (detects composer markers)

### Reality
**Neither tooling system produced the current monolith.** The current `pitchfork.toml`:
- Has NO `[generated file]` header
- Has NO `# ---- project:` separators
- Has NO schema URL stamp
- Has hand-edited blocks (coyote.env, custom readiness commands, etc.)

The D2 infrastructure (`parent.toml`, `projects.toml`) exists but is **stale and broken** — most `projects.toml` paths point to non-existent directories (17 of 31 project paths are MISSING on disk).
