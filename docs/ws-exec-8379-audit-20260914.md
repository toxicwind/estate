# ws-exec port 8379 — forensic audit + tunnel (2026-09-14)

Author: audit subagent (depth-1) for Shingle. Chris confirmed: **8379 is the
service's default and stays exactly as-is** (standing rule: if a port is a
service's default, leave it in place and tunnel to it rather than moving it).
Phase 2 (tunnel 25379 -> 8379) implemented, raced, verified live below.

## WTF happened (summary)

- TCP 8379 on awrawr-pc is the **default port** of `awrawr-ws-exec`, the
  stdlib-asyncio WebSocket exec bridge (`~/awrawr_ws_exec.py`, pitchfork daemon
  `sovereign/awrawr-ws-exec`, funnel `/exec-ws -> 127.0.0.1:8379`). Nothing
  external ever conflicted with it.
- The "port conflict" was **100% self-inflicted**. The deploying session appended
  the pitchfork.toml stanza at 16:54:29 MDT, then ran `pitchfork start
  awrawr-ws-exec` **twice within 14 seconds** (16:54:47 and 16:55:01), plus a
  `restart` at 16:56:30. The racing duplicate spawns died with EADDRINUSE, and
  each loser's death **overwrote the winner's healthy "running" record** in the
  supervisor's bookkeeping with "errored"/pid 0.
- Ever since (16:56:28 -> 20:00:54+ MDT) the supervisor's **20-second retry loop**
  has spawned a doomed duplicate every ~20 s (**465 retries**, 930 supervisor-log
  lines): each dies on EADDRINUSE against the live child, each refreshes the
  "errored" lie in `pitchfork list`.
- The live server never stopped serving: PID 2937331 (spawned 19:56:44 by the
  retry loop, upserted "running") holds 127.0.0.1:8379 — proven by root strace
  (accept4/getsockname/HTTP 400 on bad handshake/real WS frames/SIGCHLD reaps)
  and live command execution.
- At 19:56:43-45 a **second session** (unknown, HTTPS transport) ran
  `kill 2934482 && pitchfork restart` while the parent (WS transport) was also
  repairing. The foreign restart's spawn (2937332) raced the retry loop's spawn
  (2937331) by **one second**, lost on EADDRINUSE, and its death clobbered the
  bookkeeping. Two operators, one daemon, zero coordination — during a fleet
  freeze.
- Phase 2: TCP tunnel **127.0.0.1:25379 -> 127.0.0.1:8379** is live,
  supervisor-managed (`sovereign/ws-exec-tunnel`, pid 2945237), race-won and
  verified end-to-end. 8379 and the ws-exec process were never touched.

## What humans missed (top findings)

### 1. The list-lying mechanism — proven from the supervisor's own log
`pitchfork list` does not show daemon health; it shows the supervisor's last
bookkeeping upsert. At 19:56:44 the retry loop spawned 2937331 -> bound 8379 OK
-> upserted `pid: 2937331 status: running`. **One second later** (19:56:45) a
concurrent CLI `restart` spawned 2937332 -> EADDRINUSE -> exit 1 -> the
supervisor processed the death and upserted `pid: 0 status: errored`,
**clobbering the healthy record**. Every 20 s retry since spawns another doomed
duplicate that re-affirms "errored". The daemon is healthy; the bookkeeping is
poisoned by a last-writer-wins upsert with no pid validation (the dying pid is
never checked against the tracked pid).

### 2. Two sessions were doing surgery on the same daemon simultaneously
Audit-log transports prove it: parent via `ws`, unknown session via HTTPS
(empty transport). 19:56:43Z: `kill 2934482 && pitchfork restart
sovereign/awrawr-ws-exec` (foreign) while the parent ran its own restarts
19:51-19:57. The pid churn 2315871 -> 2934482 -> 2937331 in ~2 minutes was two
operators stepping on each other, not one flapping service. The foreign
restart's spawn is the bullet that killed the bookkeeping (finding 1).

### 3. `pitchfork` is two different binaries depending on PATH — and config is CWD-dependent
- Bridge default PATH -> `/home/toxic/.local/share/mise/installs/pitchfork/2.16.0/pitchfork`
  (matches the running supervisor, started 16:20:24 from that path).
- With mise shims on PATH -> **2.25.0** (`latest` -> `./2.25.0`).
- `pitchfork restart` from /home/toxic: "not found in config or state"; from
  /home/toxic/sovereign: acts on the daemon (or hangs ~63 s on IPC and then acts
  **anyway** — the 2.25.0 CLI's restart timed out but the supervisor executed
  the spawn, a likely source of phantom duplicates: the operator thinks it
  failed and retries).
- Operators get different binaries AND different configs depending on shell
  setup. Standing footgun: pin one binary and always run from /home/toxic/sovereign.

### 4. The retry loop was a hot loop, not a state (bonus)
Nobody noticed "errored" was being **refreshed every 20 s** for 3+ hours. Also,
the audit log's daily compaction ate the 16:54-17:04 launch evidence; only an
earlier timeline.txt captured the double `pitchfork start`.

## The EADDRINUSE self-clash root cause

Not an external service. Not IANA `cruise-diags` (dead assignment; nothing on
the box ever held 8379 except ws-exec itself; the cell is clean). The clash is
the supervisor fighting itself:

1. `retry = true` + 20 s retry loop + `auto = ["start"]`.
2. Every manual `pitchfork start`/`restart` — especially the double-start at
   16:54:47/16:55:01 and the 19:56:43 foreign restart — fires a spawn outside
   the loop's cadence.
3. Two spawns within the same second -> the second gets EADDRINUSE -> exit 1.
4. The supervisor's upsert is last-writer-wins with no pid validation -> the
   loser's death overwrites the winner's "running" with "errored"/pid 0.
5. The loop, seeing "errored", spawns again in 20 s -> the live child (never
   reaped, still serving) kills the new spawn -> back to 4. Perpetual.

The 2.25.0 CLI's 63 s IPC timeout made it worse: the operator thought `restart`
failed, but the supervisor executed the spawn anyway — phantom duplicates.

## CLI 2.25.0 vs supervisor 2.16.0 — consequences observed

- Same command name, two binaries (PATH-dependent). Supervisor runs 2.16.0;
  shim users get 2.25.0.
- `restart` via the 2.25.0 CLI timed out on IPC after 63 s, yet the spawn
  executed -> operators retry "failed" commands -> duplicate spawns.
- `pitchfork run` via the **2.16.0** CLI (bridge default PATH, no shim export)
  worked cleanly: registered, readiness-checked ("TCP port 25379 is
  listening"), supervised.
- `pitchfork list`/`status` disagree with `ss`/`ps` ground truth whenever the
  bookkeeping is clobbered (see finding 1).

## Phase 2 — the tunnel (127.0.0.1:25379 -> 127.0.0.1:8379)

**Goal**: TCP forwarder on 127.0.0.1:25379 -> 127.0.0.1:8379, byte-transparent
(WS handshake + frames pass through untouched). 25379 was free as of 19:57 MDT.
8379 and the ws-exec process untouched; funnel /exec-ws unchanged; additive only.

**Race** (5 samples each; real WS `echo TUNNEL_PROBE_OK` command through the tunnel;
probe borrows the handshake + framing code from `~/awrawr_ws_exec.py`):

| candidate | bind | total_ms per sample | mean |
|---|---|---|---|
| A: stdlib-asyncio Python (`/home/toxic/ws-exec-tunnel.py`) | :25379 | 2.9, 2.5, 2.6, 2.4, 2.3 | ~2.5 |
| B: `socat TCP-LISTEN:25380,bind=127.0.0.1,reuseaddr,fork TCP:127.0.0.1:8379` | :25380 | 48.9, 48.5, 49.2, 45.3, 44.1 | ~47 |
| baseline direct :8379 | :8379 | 2.5, 2.3, 2.5 | ~2.4 |

All samples correct (exit 0, stdout `TUNNEL_PROBE_OK`). **Winner: A** — adds
~0.1 ms vs direct (noise), 20x faster than socat here (consistent ~45 ms
overhead, likely delayed-ACK interaction in socat's fork-per-connection path),
stdlib-only matching house style (`ws_exec.py`).

**Persistence story (honest)**:
- The running supervisor (2.16.0) has **no reload mechanism**: no `reload`
  subcommand, zero inotify watches on its fds, and the 16:54:29 precedent shows
  new toml sections need a manual `pitchfork start`. Supervisor restart is
  forbidden (Chris).
- So the toml section takes effect on the **next supervisor start** (durable, in
  git). Until then the `run`-registered daemon is the live one (in-memory only —
  dies with the supervisor, at which point the toml definition takes over
  cleanly; no overlap, no duplicate, because the old child dies with the old
  supervisor).
- If the tunnel process dies before then, the supervisor's retry loop respawns
  it (same mechanism as other daemons; verify with `pitchfork status
  sovereign/ws-exec-tunnel`).
- Re-establish manually (if ever needed):
  `cd /home/toxic/sovereign && pitchfork run ws-exec-tunnel --port 25379 -- /usr/bin/python3 /home/toxic/ws-exec-tunnel.py`
  or without pitchfork:
  `setsid nohup /usr/bin/python3 /home/toxic/ws-exec-tunnel.py >/home/toxic/ws-exec-tunnel.log 2>&1 < /dev/null &`
- What survives a supervisor restart: the toml definition (auto-starts). What
  doesn't: the `run` registration (cleanly superseded by the toml one).

## Recommendations

1. **Keep 8379 as the ws-exec default forever; tunnel instead of moving**
   (Chris's rule — now demonstrated with 25379).
2. **Stop hand-starting pitchfork daemons during incidents.** The double-`start`
   at 16:54:47/16:55:01 caused this entire 3-hour saga. One start; then watch
   `ss`/`ps`, not `pitchfork list`.
3. **Never trust `pitchfork list` alone** — verify with `ss -tlnp` +
   `ps -o ppid=` (ppid == supervisor pid) + the supervisor's own log
   (`~/.local/state/pitchfork/logs/pitchfork/pitchfork.log`).
4. **Pin the pitchfork binary**: one version on PATH everywhere (or always the
   2.16.0 install path that matches the supervisor), and always run management
   commands from /home/toxic/sovereign. The PATH/CWD lottery caused real damage.
5. **Coordinate during incidents**: the 19:56:43 foreign kill+restart raced the
   parent's own repair. One operator per daemon per incident.
6. **Fix the supervisor's upsert**: last-writer-wins with no pid validation lets
   a racing duplicate's death clobber a healthy child's "running" status
   (upstream or wrapper fix; out of scope here).
7. **Align CLI/supervisor versions** at the next authorized maintenance window
   (requires supervisor restart — forbidden now; tracked as tech debt).
8. The 20 s retry loop is fine for genuinely dead daemons, but log the dying pid
   next to each upsert so the clobber is visible next time.
